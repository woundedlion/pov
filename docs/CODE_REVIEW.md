# Holosphere / daydream — Comprehensive Code Quality Review

**Date:** 2026-07-31
**Repositories:** `Holosphere` (C++ engine, Teensy firmware, WASM target) · `daydream` (web simulator)
**Method:** Nineteen independent review agents, each assigned a disjoint component, each required to read every in-scope file in full and to validate every candidate finding against the cited code (and against the existing test suite) before reporting it. Speculative and already-handled candidates were discarded at the agent level.
**Out of scope:** `core/engine/effects_legacy.h`, `targets/Holosphere/Holosphere.ino`, `core/math/rotate.h`.

**Result:** 287 validated findings. **No P0 defects.** 16 P1, 107 P2, 164 P3.

---

## 1. Executive Summary

This codebase is in strong health. Across nineteen independent reviews of roughly 165,000 lines of C++ and 27,000 lines of JavaScript, not one agent found a P0 — no memory corruption in a shipping path, no data race in the ISR/main-loop handoff, no numerical instability in the shipping parameter envelopes, no architectural defect requiring redesign.

The defects that were found cluster into four recognizable groups:

1. **Gate and oracle integrity** (the largest and most consequential group). Several gates that exist specifically to prevent silent regressions can currently pass when they should not: the Teensy size gate can print `PASS` from an uncalibrated fallback; the effects assertion floor is measured at the QUICK tier and is therefore blind to all 44 FULL-tier cases; the schematic-parity gate defaults to an empty diagnostic list; and a dozen or so individual assertions across both test suites were proven — several by actual mutation testing — to be incapable of failing.

2. **Untested seams in otherwise well-tested subsystems.** `Subtract`/`Intersection` interval composition, the `Face::pole_touch` boundary branch, the `SinglePass` rasterizer, both `setEffect` rejection branches in the segment worker, and the WASM growth→detach→re-fetch sequence are all reachable production paths with no direct coverage.

3. **Comment and documentation drift.** Roughly 40 findings are stale or factually wrong comments, docstrings, and README claims. Most are harmless individually; a few actively mislead (a `#error` citing a contract the spec explicitly rejected, a "two lines to add a test" instruction that produces a red CI, `HS_TEST_BUILD` described as a buffer tweak when it is a 27× arena inflation).

4. **PCB fabrication tooling**, which is the weakest component by a clear margin (C+ / B−) and carries three of the sixteen P1s. It is the one place where a defect could produce physically wrong hardware.

Everything else — the rendering engine, the color pipeline, the memory model, the hardware drivers, the animation system, the effects — is A-grade work with polish-level findings.

### P1 — High

1. ✅ **Teensy size gate prints `PASS` and exits 0 from the uncalibrated fallback** — `tools/teensy_gate_extra.py:55-63, 82-90, 116-119`. `_find_teensy_size()` probes only bare names on `PATH`, but `teensy_size.exe` ships in `~/.platformio/packages/tool-teensy/` and is not on `PATH`. On failure `run_gate` falls back to VMA-bucketed `size -A` totals and exits 0 with an indistinguishable `PASS`, while the CLI deliberately returns `EXIT_UNCALIBRATED_PASS = 3` for exactly this state. Both `docs/agent_workflow.md` §4 and the pre-commit hook gate on that printed `PASS`. Resolve the tool from the platform package before giving up; if the fallback is still taken, exit with the advisory code or hard-fail a budgeted env. Note `tools/teensy_gate_tests/test_teensy_gate.py:999` currently codifies the wrong behaviour and must be updated with it.

2. ✅ **A missing `teensy_size` makes phantasm fail as a budget violation, not a tooling break** — `tools/teensy_gate.py:368-375`, `teensy_gate_extra.py:86`. The `size -A` fallback returns no `components` key, so phantasm's `ram1.components.code` ceiling hits `component-missing` and exits 1 with a message pointing at a renamed field or a code-size regression. Under finding 1, the same missing-tool condition silently passes holosphere and red-flags phantasm for the wrong reason. Detect the fallback + declared-components combination in `run_gate` and exit 2 before calling `evaluate`.

3. ✅ **`MeshOps::fromSolidName` is the one WASM boundary entry with no tooling-arena room check** — `targets/wasm/wasm.cpp:862-873`. Its two siblings (`apply`, `classifyFaces`) both gate on `mesh_op_output_over_arena` and return `nullptr`; this one calls `Solids::get_by_name` straight into `tooling_arena`, whose exhaustion path is `HS_CHECK(false)` → `__builtin_trap` → whole-module abort with no JS recovery. The arena is only rewound by an explicit `clearToolingMemory()`, so seeds accumulate permanently across a design session in `solids.html`. Generate into `tooling_scratch_a` first, gate on the predicted finalized size, then finalize — returning `nullptr` with the same reclaim hint the other two emit.

4. ✅ **Schematic-parity gate passes silently when the DRC report has no parity section** — `hardware/phantasm/gen/fab.py:258`. `report.get("schematic_parity", [])` defaults to empty, so a flag rename or schema change yields `parity: board matches schematic, 0 known differences` on a board that was never checked, and gerbers from a stale board ship. Its sibling `require_clean_drc` gets this right by *requiring* both summary lines. Require the key, and floor the count at `len(KNOWN_PARITY_ITEMS)`.

5. ✅ **`pcb.py --unplaced` rewrites the tracked Teensy footprint library with no `--force` guard** — `hardware/phantasm/gen/pcb.py:655-663`. Unplaced mode correctly skips `require_writable` for its own output, then unconditionally rewrites `phantasm.pretty/Teensy4.0.kicad_mod` — a tracked file the committed, routed `phantasm.kicad_pcb` resolves against. The project has already been bitten once by a Teensy footprint change invalidating the routed board. Route the write through `require_writable`, or emit into `unplaced/phantasm.pretty/`.

6. ✅ **The generated board declares 2 copper layers while its zones and fab exports assume 4** — `hardware/phantasm/gen/pcb.py:564-573, 590`. The emitted `(layers ...)` block lists only `F.Cu` and `B.Cu`, but every mounting-hole keepout zone is emitted on `"F.Cu" "In1.Cu" "In2.Cu" "B.Cu"` — two undeclared layers — while `fab.GERBER_LAYERS` plots `In1.Cu,In2.Cu` and spec R-SI-1 requires SIG/GND/GND/SIG. The 4-layer upgrade exists only in `stackup.py`, a KiCad-Python-only post-pass hard-wired to one input path. Emit the 4-layer stack and the `(stackup ...)` block directly from `pcb.py`.

7. ✅ **The effects assertion floor is blind to the entire FULL tier** — `tests/run_tests.cpp:135`, `tests/test_effects.h:4367`. The floor `18742433` equals the QUICK-tier count, so all 44 case calls and both 288×144 roster sweeps inside `if (effects_full_suite())` could be deleted and the module would still clear it in CI — defeating the mechanism's stated purpose for exactly the cases CI is designated authoritative for. 8. ✅ **Every simulated board in the sync test is born in perfect phase, making the phase-snap oracles near-vacuous** — `tests/test_pov_sync.h:1123`. `Sim`'s constructor assigns an identical `phase0` to all boards, so downstream boards start aligned and diverge only by crystal ppm. 25. ✅ **`Face::pole_touch` / `PoleHit::BOUNDARY` has no test coverage** — `core/render/sdf.h:3020, 3240`. 26. ✅ **`point_rows`/`point_cols` hoisting is gated on a cull trait that does not mean what it is used for** — `core/render/plot.h:1602-1608`, trait at `:1036`, doc at `:1248`. The doc says the hoist requires "no world stage re-positions the plot"; the code enforces `!P::has_world_cull`, i.e. "no stage defines `cull_edge`". `World::Mobius` and `World::Hole` both re-position and define no `cull_edge`. 27. ✅ **`Plot::rasterize` has no `prepared_for(canvas)` trap** — `core/render/plot.h:1291-1306` vs `:3566`, `filter.h:1384-1392`. `ParticleSystem::draw` and `draw_fused_vertex` both `HS_CHECK` it; `rasterize` — used directly by `ShapeShifter::draw_sampled` — does not, leaving only a device-stripped `assert` inside `plot()`. Because the canvas double-buffers, a stale `base` is the buffer the display ISR is scanning out, so the failure mode is silent tearing. Add the `if constexpr (requires ...)` check at the top of `rasterize` and drop the two duplicates.

28. ✅ **`Timeline::clear()` from a completion callback destroys the executing callable before its trap fires** — `core/animation/timeline.h:164-175, 374-402`. `step()` invokes `post()` (user code) and only afterwards destroys the event; a `clear()` inside that callback runs `destroy_events()` → `obj->~A()`, freeing the `Fn<void(), 24>` whose `operator()` frame is still live. The guard that names `clear()` as the hazard is evaluated after `post()` has returned. Add a `stepping` flag set around `step()`'s body and trap at the *top* of `clear()`; add a death case.

29. ✅ **Generic `angle_between()` on Dynamo's per-fragment path puts two `HS_CHECK` traps inside the per-pixel loop** — `effects/Dynamo.h:189`. `color()` runs per plotted point and per trail point replayed by `flush()` — up to 29,000 points per frame. Replace with `fast_acos(hs::clamp(dot(v, palette_normal), -1, 1))`.

290. ✅ **`SDFShape`'s `thickness` requirement is vestigial — the whole propagation graph has no terminal consumer** — `core/render/sdf.h:479`. ## 5. Recommended Sequencing

**First (correctness and gate integrity):** 1–16 in order. Findings 1, 2 and 7 are the highest leverage — they are gates currently capable of reporting green on a real regression, so every other fix lands on a firmer floor once they are closed. Findings 4, 5 and 6 are the only findings in the review that could produce physically wrong hardware.

**Second (unbounded writes and abort paths):** 3, 30, 104, 105, 10. These are the memory-safety findings; none is currently reachable in a shipping path, but each is one refactor away.

**Third (test-oracle repair):** 8, 9, 12, 13, 14, 49–68, 76–85. Work these as a batch — several share a root cause (an oracle copied from the implementation, or a fake permissive enough to make the assertion vacuous), and fixing them individually will otherwise reintroduce the same pattern.

**Fourth (design-doc drift):** findings 242–263 first — these are documents whose banners or bodies would send a successor to redo landed work or re-attempt something the tree already solved, which is the most expensive kind of documentation defect in a project that relies on its ledgers this heavily. Findings 242–244 (`opchain_morph_spec.md`), 245–247 (`meshfeedback_smoke_optimization.md`) and 248–250 (`selective_o3_spec.md`) are the three worst files and are worth a rewrite rather than a patch.

**Fifth (comment and README drift):** the ~40 findings in 89–98, 117–121, 143–160 and 225–241, plus the citation-rot group 264–287. Individually cheap and sweepable in one or two passes; findings 89–98 and 158–160 actively mislead and should lead. Findings 261, 262 and 266 are mechanical and can be scripted.

**Sixth (polish):** everything remaining, at whatever cadence suits.
